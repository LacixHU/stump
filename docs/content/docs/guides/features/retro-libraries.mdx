# Retro computer libraries

Stump can catalog single-file disk and tape images for classic computers and play them in the browser via WASM emulators. The server only serves files and optional firmware bytes—it does **not** run emulators or stream video.

## Supported formats (MVP)

| Platform     | Extensions                                         |
| ------------ | -------------------------------------------------- |
| Commodore 64 | `d64`, `t64`, `prg`, `g64`, `tap` (with path hint) |
| ZX Spectrum  | `tzx`, `z80`, `sna`, `tap` (with path hint)        |
| Amiga        | `adf`, `adz`                                       |

These extensions are registered globally (like PDF). Create a library with type **Retro** so auto-metadata (when enabled) targets the right providers.

## Folder layout

Prefer nested folders (library pattern **Nested** is the default when you pick Retro):

```text
/Retro/
  C64/Last Ninja/Last Ninja Side A.d64
  C64/Last Ninja/Last Ninja Side B.d64
  Spectrum/Manic Miner/manic.tap
  Amiga/Lemmings/Lemmings.adf
```

Each game folder becomes a **series**; each disk/tape file becomes **media**. Multi-disk games share one series.

### Ambiguous `.tap` files

`.tap` is used by both C64 and Spectrum. Resolution order:

1. Path segments containing `c64` / `commodore` → C64; `spectrum` / `zx` / `sinclair` → Spectrum
2. Else inherit platform from other media in the series
3. Else default to **C64** (name folders clearly to avoid this)

## C64 emulator

In-browser C64 play uses **[c64-ready](https://www.npmjs.com/package/c64-ready)** (MIT; WASM based on c64.js / lvllvl). Assets are served from `/retro/c64/` (`c64.wasm`, audio worklet).

Supported load types in this core: **`.d64`**, **`.prg`**, **`.crt`** (`.t64`/`.g64` are treated as disk-like when possible). Click the canvas for keyboard focus; default input mode is mixed joystick + keyboard.

### Controls

- **Reset** (toolbar) performs a C64 hard reset, then restarts the game the same way it was started the first time. The inserted disk stays in the drive; it does not destroy the emulator.
- **Settings** (toolbar) sets input mode (`mixed` / `keyboard` / `joystick`), joystick port (1 or 2), and disk speed. Click the canvas once if audio is muted (browser autoplay).
  - **Instant** (default) reads the first program out of the `.d64` directory and writes it straight into C64 memory, so a game that would take one to two minutes to load off the emulated 1541 starts in well under a second. The disk stays in the drive, so games that load further data during play still work — those transfers are warped instead (roughly 10x; gameplay itself stays at original C64 speed). Disks whose first file is not a BASIC-startable program fall back to a normal warped `LOAD"*",8,1`.
  - **Authentic** is real 1541 timing, with no warping and no injection.
  - Disk speed does not apply to `.t64` tapes or bare `.prg` files: there is no drive involved, so they are always written straight into memory. The program is started with `RUN` when it loads at `$0801`, and with `SYS <load address>` otherwise — which is how most machine-code tape rips start.
- On-screen controls show on touch/narrow screens, or while editing the overlay. Desktop fullscreen with a keyboard does not show them.
- Users with **Manage library** can **Edit overlay** (Settings): pick any C64 key or joystick control from the on-screen keyboard and drag them into place. Save writes series-folder `controls.json`.
- The disk list **inserts** a new image into the running session (no reboot, no auto `LOAD`/`RUN`). Use this for multi-disk games.

Optional overlay layout lives in a series-folder `controls.json` next to the disks:

```json
{
	"keys": [
		{ "id": "up", "x": 0.16, "y": 0.7 },
		{ "id": "fire", "x": 0.88, "y": 0.82 },
		{ "id": "runstop", "x": 0.42, "y": 0.92 }
	]
}
```

`x` / `y` are 0–1 fractions of the playfield. Older `{ "extraKeys": ["f1"] }` files still work (defaults plus extras). `restore` is not functional in this WASM build.

| Action                                  | Permission      |
| --------------------------------------- | --------------- |
| `GET /api/v2/media/{id}/retro-controls` | Library access  |
| `PUT /api/v2/media/{id}/retro-controls` | `ManageLibrary` |
| `GET /api/v2/media/{id}/save-state`     | Library access  |
| `PUT /api/v2/media/{id}/save-state`     | Library access  |
| `DELETE /api/v2/media/{id}/save-state`  | Library access  |

## Play vs download

| Action                                                     | Permission                                   |
| ---------------------------------------------------------- | -------------------------------------------- |
| **Play** (`GET /api/v2/media/{id}/play-file`)              | Library access only (same as reading a page) |
| **Overlay keys** (`GET /api/v2/media/{id}/retro-controls`) | Library access only                          |
| **Save overlay** (`PUT /api/v2/media/{id}/retro-controls`) | `ManageLibrary`                              |
| **Save state** (`*/api/v2/media/{id}/save-state`)          | Library access only (each user's own save)   |
| **Download** (`GET /api/v2/media/{id}/file`)               | `DownloadFile`                               |

`play-file` only allows retro extensions (defense in depth so non-download users cannot pull EPUBs/CBZs through that path).

## Amiga firmware (Kickstart)

Amiga emulation needs user-supplied Kickstart ROMs. Never commit or bundle BIOS files.

1. Set `STUMP_FIRMWARE_DIR` (default: `{config_dir}/firmware`).
2. Place required Kickstart files as documented by the pinned Amiga WASM build (e.g. `kick33180.A500`, `kick34005.A500`).
3. The player fetches them via `GET /api/v2/firmware/{file_name}` (authenticated; basename only—no path traversal).

If firmware is missing, the catalog still works; Play shows setup instructions.

## Covers / thumbnails

Retro files have no internal pages, so Stump **cannot** generate a cover from the disk image itself.

**Automatic covers work when you provide a local image next to the game:**

| Location                     | Filenames                                                                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Same folder as the disk/tape | `{game name}.jpg` / `.png` / `.webp`, or `cover.jpg`, `folder.jpg`, `poster.jpg`, `front.jpg`, `box.jpg`, `boxart.jpg` |
| Parent (series) folder       | same `cover` / `folder` / … names                                                                                      |

Then run a library **scan** (or thumbnail generation). Stump copies/resizes the sidecar into the thumbnail store.

If no sidecar is found, Stump searches Wikipedia via the MediaWiki API in [Category:Video game covers](https://en.wikipedia.org/wiki/Category:Video_game_covers) (and platform subcategories such as Commodore 64 / ZX Spectrum / Amiga). A matching cover is downloaded and stored as the thumbnail.

Sidecar files always win over Wikipedia. Many Wikipedia covers are fair-use; only use this for your own library. Manual upload on the book manage page still works.

## Save states

A save state is the complete memory image of the emulated machine — CPU, RAM, and chip
state — so restoring one drops you back exactly where you were, mid-level and all.

Save states are stored **on the server**, one per user per game:

- They follow you between devices and browsers. Save on the desktop, load on a tablet.
- They are private. Each user has their own slot for a game; no one else can read or
  overwrite it, and there is no shared or "server-wide" save.
- They survive clearing site data, since nothing is kept in the browser.

Use the **Save state** and **Load state** buttons in the player header. There is one slot
per game: saving again replaces the previous snapshot. For a multi-disk game, the slot
belongs to the book you opened, so swapping disks mid-game does not hide the save behind
a different disk.

Snapshots are written to `save_states/{media_id}/{user_id}.savestate` under the Stump
config directory, with a small metadata row in the database. Deleting a library removes
the snapshots belonging to its books. The server accepts snapshots up to **16 MiB**,
which is comfortably above a C64 snapshot (a few hundred KiB) and an Amiga one
(a few MiB).

Save states depend on the emulator core supporting snapshots. The C64 core does; the
Spectrum and Amiga shells do not yet, and the player will say so.

## Legal

You must supply your own game images and BIOS/firmware. Stump does not distribute copyrighted ROMs or disk images.

## OPDS

OPDS entries for retro media expose **file acquisition** only (no page stream links). Page-based OPDS reading does not apply when `pages = -1`.
